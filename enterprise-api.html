The challenge

Why were teams rebuilding APIs instead of reusing what already existed?

The API Marketplace was live, but discoverability, trust, ownership and incentives were getting in the way of reuse. The engagement aimed to diagnose the human and organisational causes and give leadership an evidence base for a proposed community and operating model.

What I did

Designed interviews to uncover real behaviour.

I created a protocol that moved from context to recent examples, delivery friction, culture and future needs. Scenario prompts encouraged participants to describe what they actually did rather than offer abstract opinions. I also helped facilitate affinity mapping and the ideation session.

What the research revealed

The blockers were socio-technical, not just a search problem.

Discovery depended on people

Teams relied on personal networks and tribal knowledge to find existing capabilities.

Ownership was unclear

Uncertainty about accountability reduced confidence in reuse.

Rebuilding felt safer

Delivery pressure and familiar habits made duplication an easy default.

Incentives worked against reuse

Recognition favoured delivering something new more than contributing to shared capability.

From evidence to recommendation

One research thread, made actionable.

Evidence

People were the search system

Participants described relying on personal networks and tribal knowledge to find APIs.

Insight

Discoverability was also about trust

Finding an API was not enough when ownership, support and suitability were unclear.

Design implication

Make ownership visible

Improve owner/contact information and help consumers assess whether an API is safe and appropriate to reuse.

This is one example of the reasoning path; it represents a research-led recommendation, not a tested or shipped change.

Decision trade-offs

Improve reuse without adding another layer of friction.

Option considered

Improve search alone

Potentially faster to deliver, but it would not resolve uncertainty about ownership, support or whether an API was safe to reuse.

Chosen direction

Pair discovery with trust signals

Recommend clearer ownership, contact paths and suitability information alongside discoverability improvements.

Trade-off to test

More context vs. more maintenance

Additional metadata helps consumers only if API owners can keep it accurate. Co-design the minimum useful fields and ownership process before implementation.

How I would evaluate the recommendation

  • Task: ask API consumers to find a suitable existing API and identify its owner.
  • Measures: task success, time to find, confidence in suitability, and incorrect reuse decisions.
  • Operational check: measure metadata completeness and freshness with API owners.
  • Decision rule: refine the listing if people find an API but cannot confidently assess ownership or fit.
Design implications and limits

Make reuse easier to discover, trust and value.

The findings pointed toward clearer ownership and contacts, more discoverable API information, lower trust friction and recognition for reuse. These are research-led recommendations—not shipped product changes.

What I would do next

Co-design the operating model with API consumers and owners, test discovery tasks against real workflows, and define measures for reuse, time-to-discovery and duplicated effort.

Outcome: a qualitative evidence base and strategic direction for leadership. The intervention and its impact were not validated in production.
